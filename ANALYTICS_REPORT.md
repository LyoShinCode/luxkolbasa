## 1. Исходная постановка задачи

### 1.1. Текст ТЗ от заказчика

> Одностраничное веб-приложение для Desktop с красивым дизайном в двух темах (светлая/тёмная).  
> Вверху надпись «Мир ЛюксКолбасы».  
> Остальная часть делится по вертикали 2/3 к 1/3.  
> Левая часть: три слайдера 0–100 (соль, шпик, перец) с числовыми полями, кнопка «Создать».  
> Правая часть: затемнённый прямоугольник для готовой колбасы.  
> При нажатии «Создать» или Enter — картинка колбасы + псевдоитальянское название.

## 2. Ключевые аналитические решения

### 2.1. Выбор архитектуры

ТЗ содержало противоречие: «веб-приложение» + «desktop» + «Docker». Desktop-приложения (JavaFX/Compose) не запускаются в контейнере Docker. Было принято решение:

**Клиент-серверная архитектура:**
- **Backend:** Kotlin + Ktor (Netty) — REST API + раздача статики
- **Frontend:** Vanilla HTML/CSS/JS в браузере (это и есть «desktop-подобный» UX)
- **Упаковка:** Docker multi-stage (стадия сборки на JDK → рантайм на JRE)

Обоснование: схема работает в контейнере, масштабируется, соответствует реальному промышленному стеку в российском финтехе (Тинькофф, Альфа).

### 2.2. Генерация колбасы

Белое пятно: **«Картинка с колбасой — откуда?»**

Варианты:
1. Стоковые фото — лицензионные риски, визуальная однородность
2. Одна фиксированная картинка — скучно, не зависит от рецептуры
3. **Процедурный SVG** — выбрано

Реализация: сервер генерирует детерминированный `seed` из параметров рецептуры, фронтенд рисует колбасу на его основе. Цвет мяса, светлые вкрапления (шпик), тёмные зёрна (перец), кристаллики (соль) — всё зависит от входных данных. Одна рецептура = одна колбаса всегда.

### 2.3. Генерация имени

**Детерминированная** генерация псевдоитальянских названий на сервере. Seed = функция от параметров. Это:
- устраняет путаницу («почему при тех же параметрах другое имя?»),
- даёт воспроизводимость для баг-репортов,
- упрощает тестирование.

## 3. Таблица принятых допущений

| № | Белое пятно в ТЗ | Риск | Решение |
|---|---|---|---|
| 1 | «Веб» + «desktop» + «Docker» | Неправильная платформа | Клиент-сервер + Ktor |
| 2 | «Делится по вертикали 2/3 к 1/3» | Неверная раскладка | `grid-template-columns: 2fr 1fr` (по контексту «левая/правая») |
| 3 | «Enter» без уточнения где | Двойные срабатывания | Глобальный hotkey, исключая фокус на кнопках |

| 5 | Имя: детерминированное или случайное | Несогласованность | Детерминированное, seed на сервере |
| 6 | Откуда картинка | Лицензии / скучно | Процедурный SVG |
| 7 | Тема по умолчанию, запоминание, FOUC | Мигание, невидимая витрина | `prefers-color-scheme`, `localStorage`, inline-скрипт до рендера |
| 8 | Один результат или галерея | Переусложнение | Один результат, заменяет предыдущий |

## 4. Нефункциональные требования

| Категория | Решение |
|---|---|
| **Устойчивость** | Валидация на двух уровнях (клиент + сервер), обработка сетевых ошибок |
| **Производительность** | Детерминированный PRNG (mulberry32), кэш слоёв Docker |
| **Доступность** | `aria-label`, `aria-live`, `focus-visible`, `prefers-color-scheme` |
| **Масштабируемость** | REST-архитектура, один метод API |
| **Упаковка** | Multi-stage Docker (JDK → JRE, ~245 МБ) |

---

## 5. Стек технологий и его обоснование

- **Kotlin 2.0 + Ktor 3** — запрос ТЗ на JVM-стек; Ktor легковеснее Spring Boot
- **Vanilla JS без фреймворков** — минимизация зависимостей, проект учебный
- **Gradle с toolchain auto-provisioning** — воспроизводимость сборки на любой машине без ручной установки JDK
- **Docker multi-stage** — итоговый образ без компиляторов, быстрый деплой
